Backupkit reads one `config.jsonc` describing your remotes, targets, schedules, and retention. This page lists every field and its default.

`backupkit init` writes a commented starter you can edit in place - that is the fastest way in. Come here when you need the details.

## The file format

The config is **JSONC**: strict JSON plus three tolerances - `//` line comments, `/* */` block comments (they do not nest), and one optional trailing comma before a `}` or `]`. Name it `config.jsonc`; a plain `config.json` also works, since JSON is a subset.

Two rules are stricter than `JSON.parse`:

- **A duplicate key is a fatal error** naming both lines, so a shadowed remote or target can never be dropped silently.
- **Nesting is capped** at 64 levels.

The schema itself adds a third: **any key it does not know is a fatal error**, at every level - top-level, remote, target, schedule, retry, rsync, retention, logging - so a typo'd field is never silently ignored. A remote no target references is the one soft case: that is a warning, not an error.

### Where the config is found

Every command looks in the same order:

1. `--config <path>`
2. `$BACKUPKIT_CONFIG`
3. `/etc/backupkit/` - trying `config.jsonc`, then `config.json`
4. `~/.backupkit/` - same two names

A path from `--config` or `$BACKUPKIT_CONFIG` is resolved against the current directory and normalized - it may hold no `.` or `..` component, and no whitespace or quote character, because its directory becomes the default `known_hosts` location that ends up inside rsync's `-e` string. An empty `$BACKUPKIT_CONFIG` counts as unset and falls through to the probe directories. If nothing is at a path you named, that is an error, not a reason to keep looking. Having both `config.jsonc` and `config.json` in one directory is also an error, and it names both files.

**The two run modes normally keep two different files.** `/etc/backupkit/config.jsonc` is the system config - root-owned, and the only one [a service](/daemon-setup/) finds by itself, since its unit runs as root. `~/.backupkit/config.jsonc` is your own, the one [a scheduler you run yourself](/run-it-yourself/) uses. `backupkit init` writes whichever matches the identity that ran it.

That order is the same for *every* identity, though, so a `/etc/backupkit/config.jsonc` shadows every user's personal file. On a machine that has both, unprivileged commands need `--config ~/.backupkit/config.jsonc` (or `BACKUPKIT_CONFIG` in the shell profile) to reach their own.

## Top-level fields

| Field | Type | Default | Meaning |
| --- | --- | --- | --- |
| `remotes` | object | required | Machines this host talks to, keyed by short name |
| `targets` | object | required | What to back up, keyed by target name (they run in the order you write them) |
| `name` | string | `"backupkit"` | Instance label the schema accepts; nothing surfaces it yet |
| `retention` | object | keep everything | Default retention for targets that define none |
| `stateDir` | string | `/var/lib/backupkit` as root (`/var/db/backupkit` on macOS), else `$XDG_STATE_HOME/backupkit` falling back to `~/.local/state/backupkit` | Where run reports are stored |
| `logging` | object | `{ level: "info" }` | `level` (`error`/`warn`/`info`/`debug`) and an optional `file` |
| `rsyncBin` | string | tries `/opt/homebrew/bin/rsync`, `/usr/local/bin/rsync`, then PATH | Override the local rsync |
| `sshBin` | string | from PATH | Override the local ssh |

Remote and target keys have to match `/^[a-z0-9][a-z0-9._-]*$/` and be at most 64 characters.

The `stateDir` default is picked from the **identity running the command**, not from the config file. A config shared between the root daemon and your own unprivileged `backupkit status` therefore resolves to two different report directories unless you set `stateDir` explicitly - see [Root service, per-user config](/daemon-setup/#root-service-per-user-config).

## Remotes

A remote comes in one of two shapes, and they are mutually exclusive. If there is an `alias` key, it is an alias remote; otherwise it is an explicit one.

### Explicit remote

Backupkit owns the identity, loads the key, and manages known_hosts.

| Field | Type | Default | Meaning |
| --- | --- | --- | --- |
| `host` | string | required | Hostname or IPv4 matching `/^[a-z0-9_][a-z0-9._-]*$/i`, or an **unbracketed** IPv6 literal (`::1`, `fe80::1%eth0`); max 253 |
| `user` | string | required | SSH username, `/^[a-z_][a-z0-9._-]{0,31}$/i` |
| `identityFile` | string | required | Absolute path to the private key (no whitespace or quotes) |
| `port` | integer | `22` | SSH port, 1-65535 |
| `passphrase` | string | none | `"file:/abs/path"` or `"prompt"` - never the passphrase itself. **Not usable under the service** |
| `knownHostsFile` | string | `<configDir>/known_hosts` | Override the dedicated known_hosts path |
| `restrictedShell` | boolean | `false` | The remote's shell parses no quoting (an appliance account) - send bare, charset-checked words. Only usable on a target with `"jail": false` |

```jsonc
"remotes": {
    "example": {
        "host": "10.0.0.11",
        "user": "backup-reader",
        "identityFile": "/etc/backupkit/keys/example_ed25519",
    },
}
```

`passphrase` accepts only `"file:/..."` or exactly `"prompt"`. A raw passphrase or an `env:` form is rejected. The path after `file:` is validated like every other path field. See the [Security Model](/security-model/#permissions-are-checked-before-anything-talks-to-the-network) for how each form is loaded.

**A passphrase-protected key rules out the service.** `backupkit daemon` refuses to start when any configured key is encrypted - by declaration or in fact - because a service has no terminal to unlock one on. A config with this field therefore belongs to the mode you [run yourself](/run-it-yourself/), where `backupkit start` prompts once per key and then schedules identically; the alternative is giving the service a key with no passphrase. See [a service cannot hold an encrypted key](/daemon-setup/#a-service-cannot-hold-an-encrypted-key).

`host` is validated against a list of allowed characters rather than a list of banned ones, because the failure modes are quiet: a value containing `/` makes rsync read `user@host/x:/path` as a *local* path and write your archive into a relative directory, and a leading `-` or a control character reaches ssh's option parser or your terminal. A pre-bracketed `[::1]` is rejected because backupkit adds the brackets itself.

### Alias remote

An alias remote reuses a `Host` entry from your `ssh_config`. Host, user, key, port, and known_hosts all come from ssh, so the only fields it takes are `alias` and `restrictedShell` - anything else is a config error, because it belongs in `ssh_config`. (`restrictedShell` is the exception precisely because it describes the remote's *shell*, which `ssh_config` has no way to express.)

Given this in `~/.ssh/config`:

```
Host myserver
    HostName 10.0.0.11
    User backup-reader
    IdentityFile /etc/backupkit/keys/example_ed25519
```

the backupkit remote is one line:

```jsonc
"remotes": {
    "myserver": { "alias": "myserver" },
}
```

The alias has to match `/^[a-z0-9_][a-z0-9._-]*$/i`, max 64 - so no whitespace, quotes, `:`, `@`, `/`, or leading `-`, and it can never confuse rsync's `host:path` split or ssh's option parsing.

Backupkit still adds its own safety options on the command line, which override `ssh_config`. An alias remote keeps the strict host-key and no-hang behaviour even if your `ssh_config` is lax.

## Targets

Each target is keyed by name. For a snapshot target that name becomes the snapshot subdirectory; for every target it is the identifier in the logs.

| Field | Type | Default | Meaning |
| --- | --- | --- | --- |
| `mode` | `"snapshot"` \| `"mirror"` | **required, no default** | A versioned archive, or one in-place copy - see below |
| `direction` | `"pull"` \| `"push"` | required | Pull fetches from the remote; push sends to it |
| `remote` | string | required | A key from `remotes` |
| `source` | string | required | Directory to back up (pull: on the remote; push: local) |
| `destination` | string | required | Snapshot mode: the archive root. Mirror mode: the copy itself (pull: local; push: on the remote) |
| `exclude` | string[] | `[]` | rsync exclude patterns |
| `schedule` | object | `{ interval: "day" }` | When to run - see below |
| `retention` | object \| `false` | the top-level default | **Snapshot only.** Retention for this target; `false` means never prune |
| `retry` | object | `{ attempts: 5 }` | Transfer attempts per run, 1-10 |
| `minFree` | string \| `false` | `"5%"` | **Snapshot only.** Free-space floor; `false` turns the guard off |
| `rsync` | object | `{}` | Per-target rsync tuning - see below |
| `jail` | boolean | `true` (push targets) | Push only - writing it on a pull target is a config error. `false` skips the recommended `backupkit-remote` jail, and `backupkit check` prints a warning in place of the `authorized_keys` line. A push mirror **must** set it to `false`. See [running without the jail](/push-vs-pull/#running-without-the-jail) |
| `enabled` | boolean | `true` | `false` means configured but never scheduled |

### Snapshot or mirror

`mode` is the one field with no default. The two modes have opposite properties - one keeps every previous version, the other overwrites and deletes in place - so backupkit will not pick for you. A config that omits it fails validation naming the target.

```jsonc
"targets": {
    // Versioned archive: /srv/backups/web/2026-08-10T030000Z/, and one more each day.
    "web": {
        "mode": "snapshot",
        "direction": "pull",
        "remote": "example",
        "source": "/var/www",
        "destination": "/srv/backups",
    },
    // One in-place copy: /Volumes/persistance IS the tree, kept identical to the source.
    "persistance": {
        "mode": "mirror",
        "direction": "pull",
        "remote": "example",
        "source": "/home/me/persistance",
        "destination": "/Volumes/persistance",
        "schedule": { "interval": "hour" },
    },
}
```

**Snapshot** is the archive: each run writes `<destination>/<name>/<timestamp>/`, hardlinked against the previous snapshot so unchanged files cost no space, and [retention](/retention/) prunes the history on a schedule. You can restore any kept point in time.

**Mirror** is a sync: `<destination>` *is* the tree, one copy, no history. Use it to keep two clones of the same directory in step - a working directory and its copy on another machine or an external volume. What it gives up is every recovery property of the archive: **anything the source no longer has is deleted from the destination on the next run**, including a file you deleted by accident an hour ago, and there is no earlier version to go back to.

What changes for a mirror:

- `retention` and `minFree` are config errors, not silent no-ops - a mirror keeps no history to prune, and it replaces its destination rather than growing it.
- `backupkit list` and `backupkit prune` skip it, and `backupkit restore` refuses it - there is no point in time to restore.
- `backupkit status` still shows it: last result, next due, and consecutive failures all work, and `lastSnapshot` is empty.
- Its schedule window is fulfilled by its own run reports rather than by an archive listing, so the reports in `stateDir` are what keep it from re-running every tick.
- It takes no destination lock, so `backupkit unlock` always reports nothing to clear.

**A mirror will not run a transfer that has collapsed.** Before each run backupkit estimates the source, and if it holds under half the files the last successful run moved, the transfer is refused and the run is reported as `content-collapse` - the mirror is left exactly as it was. That is the case where an unmounted volume or a half-restored directory would otherwise delete the good copy. Check the source, then `backupkit run --force <target>` performs it anyway.

**A push mirror cannot be jailed** and must write `"jail": false`. The jail's forced command pins every transfer to `<destination>/<target>/<snapshot>.partial`, and that pin is exactly what keeps the `--delete` it also allows confined to the snapshot being built. A mirror writes the destination root itself, so the jail rejects it - and could not safely be taught to accept it. Mirror with `"direction": "pull"` instead wherever you can: the machine holding the copy then does the fetching, and the source needs no access to it at all.

### Path rules

Every path field has to be absolute (`~` is rejected), free of NUL and newline, and free of any `.` or `..` component - write the resolved path.

The paths that end up inside rsync's `-e` string or a remote command are stricter still: `identityFile`, `knownHostsFile`, `rsyncBin`, `sshBin`, `rsync.remoteRsyncBin`, the path after `passphrase: "file:"`, and a push `destination` additionally reject whitespace and quote characters. `source`, `stateDir`, `logging.file`, and a pull `destination` accept both, so `/Volumes/My Backups` is a perfectly good pull destination.

**Two targets may not have nesting write roots.** The write root is `<destination>/<name>` for a snapshot target and `<destination>` itself for a mirror, and no target's may equal or sit inside another's in the same place - destinations `/b` for target `a` and `/b/a` for target `b` collide, and validation says so by name rather than letting one target's archive grow inside another's. With a mirror in the mix this stops something worse than untidiness: a mirror deletes whatever its source does not have, so a mirror whose destination contained another target's archive would delete that archive on its first run.

Paths are normalized when the config loads: duplicate slashes collapse and a trailing slash is stripped, so `/srv/backups//archive/` and `/srv/backups/archive` are the same destination.

That matters most for push targets. The destination is written verbatim into the archive host's forced command as the jail root, and the jail compares it against incoming paths as a literal prefix - so an un-normalized form would be rejected on every operation.

**A push `destination` also may not contain whitespace or quote characters**, jailed or not. rsync backslash-escapes a space when it re-serializes its own `--server` argv, and the receiving side word-splits that argv. So a destination like `/Volumes/My Backups` passes validation, prints a plausible-looking jail line, lets every lifecycle command through - and then fails the actual data transfer on every run. A pull destination is purely local and is unaffected.

`minFree` is either `"N%"` (0-50) or an absolute binary size with a `K`/`M`/`G`/`T` suffix - `"500M"`, `"10G"`, `"1.5T"`. Both forms accept a decimal.

### Schedules

The `schedule` object sets the window. Anchors are optional, and each one only applies to the intervals it makes sense for.

| Field | Type / range | Valid for | Default |
| --- | --- | --- | --- |
| `interval` | `minute` \| `hour` \| `day` \| `week` \| `month` | always (required) | - |
| `intervalCount` | integer >= 1 | every interval | `1` |
| `at` | `"HH:MM"` UTC | day, week, month | `"00:00"` |
| `on` | `mon`..`sun` | week | `"mon"` |
| `dayOfMonth` | integer 1-28 | month | `1` |

Using an anchor outside its interval is a config error that names the field - `at` on a `minute` schedule, say, or `dayOfMonth` on anything but `month`.

`dayOfMonth` stops at 28 so the day exists in every month: nothing gets clamped and February is never skipped. `month` windows are real calendar months in UTC, not a 30.5-day approximation.

One example per interval:

```jsonc
"schedule": { "interval": "minute", "intervalCount": 5 }              // every 5 minutes
"schedule": { "interval": "hour", "intervalCount": 6 }                // every 6 hours
"schedule": { "interval": "day", "at": "03:00" }                      // daily at 03:00 UTC
"schedule": { "interval": "week", "on": "sun", "at": "01:00" }        // weekly, Sunday 01:00 UTC
"schedule": { "interval": "month", "dayOfMonth": 1, "at": "04:00" }   // monthly, the 1st at 04:00 UTC
```

### Retry

The only knob is how many attempts a transfer gets. The delays are fixed.

```jsonc
"retry": { "attempts": 5 }
```

`attempts` is an integer from 1 to 10, default 5. Between attempts backupkit waits 15 seconds, doubling up to a 300-second cap with plus or minus 20% jitter, and always resumes into the same `.partial` snapshot rather than starting over.

### rsync tuning

The optional `rsync` object tunes the transfer for one target. Every field is optional.

| Field | Type | Default | Effect |
| --- | --- | --- | --- |
| `compress` | boolean | `true` | `-z` compression |
| `bwlimit` | string | unlimited | `--bwlimit`, e.g. `"10M"` or a bare number (KiB/s) |
| `ioTimeoutSec` | integer | `600` | `--timeout` seconds |
| `xattrs` | boolean | `false` | `--xattrs` |
| `preserveOwnership` | boolean | `true` | Receive owner and group; `false` adds `--no-owner --no-group` |
| `preserveDevices` | boolean | `false` | Allow device and special files (rsync `-D`) |
| `remoteRsyncBin` | string | the remote's default | `--rsync-path`. Pull targets only |
| `verify` | boolean | `false` | Run a `--checksum --dry-run` pass before promoting. Separate from `restore --verify` |

Setting `remoteRsyncBin` on a **push** target is a config error: the archive host's forced command fixes the remote rsync binary, so point the jail account's own PATH at an rsync 3.2.5 or newer instead.

## Retention

The top-level `retention` object is the default for targets that do not define their own. Each field keeps one tier of snapshots, and a snapshot survives if any rule claims it.

```jsonc
"retention": {
    "keepLast": 7,
    "keepHourly": 24,
    "keepDaily": 14,
    "keepWeekly": 8,
    "keepMonthly": 12,
    "keepYearly": 3,
}
```

There are six keys: `keepLast` (the N newest snapshots) plus `keepHourly`, `keepDaily`, `keepWeekly`, `keepMonthly`, and `keepYearly`, each keeping the newest snapshot of each of the N most recent UTC buckets *that hold one*. On a minute or hour schedule, `keepLast` and `keepHourly` are what govern sub-daily density.

All counts are non-negative integers.

- Omit the object entirely and every target that sets no `retention` of its own keeps all its snapshots forever.
- Set a target's `retention` to `false` to keep everything for that target.
- An empty `{}` is rejected, because it would be ambiguous.

A target's `retention` replaces the default wholesale; the two are never merged. See [Versioning & Retention](/retention/) for how the tiers pick snapshots.
