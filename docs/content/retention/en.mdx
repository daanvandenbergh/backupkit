Every run leaves behind a dated snapshot. Retention decides how many of those you keep as they pile up. This page covers both.

## Every run is a hard-linked snapshot

A target's snapshots live at `<destination>/<target>/<timestamp>/`, one directory per run, named with a UTC timestamp.

Files that have not changed since the previous complete snapshot are hard-linked instead of copied - meaning the new snapshot points at the same data on disk rather than duplicating it. So an unchanged tree costs almost nothing, and only changed and new files take up space.

What you get is a full, browsable copy at every timestamp, for roughly the storage cost of an incremental backup. Snapshot names sort as plain strings, so "newest" is always unambiguous and history reads in order.

## A snapshot survives if any rule claims it

Retention follows a grandfather-father-son scheme: keep recent backups densely, older ones sparsely. It counts backwards through the snapshots that actually exist, never against a wall clock.

Each rule keeps one tier, and a snapshot is kept if **any** rule claims it:

| Rule | Keeps |
| --- | --- |
| `keepLast` | The N newest snapshots, no other condition |
| `keepHourly` | The newest snapshot of each of the N most recent UTC hours |
| `keepDaily` | The newest snapshot of each of the N most recent UTC days |
| `keepWeekly` | The newest snapshot of each of the N most recent ISO weeks (Monday-start) |
| `keepMonthly` | The newest snapshot of each of the N most recent UTC months |
| `keepYearly` | The newest snapshot of each of the N most recent UTC years |

Each tier walks the snapshots newest first, works out which hour, day, week, month, or year each one falls in, and keeps the first snapshot it sees in each of those buckets until it has kept N of them.

A snapshot claimed by more than one tier records every reason - for example `last` and `daily=2026-08-10`.

The starter config ships a sensible default:

```jsonc
"retention": {
    "keepLast": 7,      // the 7 newest, unconditionally
    "keepDaily": 14,    // newest snapshot of each day, 14 days
    "keepWeekly": 8,    // newest per ISO week, 8 weeks
    "keepMonthly": 12,  // newest per month, 12 months
}
```

That keeps recent history dense and thins the older end to one per week, then one per month. A year of daily backups collapses to a few dozen snapshots.

## The newest complete snapshot is always kept

Before any rule runs, the newest complete snapshot is kept with the reason `newest`. A prune can never delete your most recent backup, even if every tier is set to zero. This is a hard rule, not a side effect of how the tiers happen to work out.

## Turning retention off

Counts are non-negative integers. There are two ways to keep everything, and the difference is deliberate:

- **Omit the top-level `retention` object** to keep every snapshot of every target forever.
- **Set a target's `retention` to `false`** to keep everything for that one target, overriding the default.

An empty object (`"retention": {}`) is rejected, because it would be ambiguous - `false` is the explicit spelling. A target's `retention` replaces the top-level default outright; the two are never merged.

Schedules and retention are independent of each other. The tiers work the same however often a target runs. For `minute` and `hour` schedules, `keepLast` and `keepHourly` are what control how dense sub-daily history stays.

## Applying retention

The daemon prunes after each run, but you can do it by hand any time:

```bash
backupkit prune              # apply retention to every target now
backupkit prune --dry-run    # print the plan and stop
```

`--dry-run` shows which rule claims each snapshot and which ones would go, so you can confirm a policy before it deletes anything.

Pruning runs under the snapshot store lock, and deletion happens in two phases, so a prune interrupted halfway never leaves a half-deleted snapshot behind.

## The content-collapse tripwire

Retention picks snapshots by name and count, never by content. So a source that suddenly hands over a near-empty tree would produce near-empty snapshots, and retention would dutifully age out the ones holding your real data. That is how an archive gets destroyed from the source side without anyone running a delete.

To catch it: when a promoted snapshot's file count collapses compared to the previous one, **the automatic prune after that run is skipped**.

The snapshot itself is still stored - the data has already crossed the wire, and throwing it away would be the more destructive choice. The archive just grows until a human looks. The run is logged at error level and the collapse is recorded on the run report, so it shows up in `backupkit status` instead of passing unnoticed.

`backupkit prune` never consults the tripwire. Once you have confirmed the shrink was real - you did delete half the source, or the application moved its data directory - run it by hand and retention applies as normal.
