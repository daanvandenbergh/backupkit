Every target sets a `direction`: `"pull"` or `"push"`. It decides which machine initiates the ssh connection and which side holds the archive - and that single choice is the largest security decision in a backup setup. This page explains the two directions, why pull is the default, and what the pipeline does differently for each.

## The two directions

The `direction` field is required on every target and takes exactly two values:

- **`"pull"`** - this machine (the backup server) connects out to the remote and fetches its `source` into a local `destination`. The `source` is a path on the remote; the `destination` is a local archive root.
- **`"push"`** - this machine (the source host) connects out to the remote and sends its local `source` to a `destination` on the remote. The `source` is a local path; the `destination` is a path on the archive server.

In both cases *this* machine is the one running backupkit and opening the ssh connection. The difference is which end owns the data and which end owns the archive.

## Why pull is the safe default

Pull is recommended because it inverts the trust relationship in your favour. With pull, the backup server holds the credentials and reaches into the source host; the source host has no way to reach the archive. If the source host is compromised, the attacker has no credentials to the backup server, cannot read other machines' backups stored there, and cannot delete or tamper with existing snapshots. The archive is simply out of reach.

For a pull target the remote account only needs to be able to *read* the source, so a read-only user is enough - the starter config names its example user `backup-reader` for exactly this reason.

Push exists for the case where the source host must initiate the connection - for example when the backup server cannot route to the source, or the source sits behind NAT. Push is more dangerous because the source host now holds a credential that reaches the archive, so backupkit constrains that credential hard (see below).

## What push locks down

When you push, the key the source host authenticates with should not be an unrestricted shell key. By default backupkit expects it jailed behind a forced command, `backupkit-remote`, installed on the archive server (this is recommended, but [optional](#running-without-the-jail)). `backupkit check` prints the exact `authorized_keys` line to install:

```
restrict,command="/usr/local/bin/backupkit-remote /srv/backups" ssh-ed25519 AAAA...
```

The `restrict` prefix disables port forwarding, agent forwarding, PTY allocation, and X11. The forced command then permits only the exact `rsync --server` transfers and the handful of directory operations backupkit's snapshot store issues, each confined to the jail root you name. Anything else the key tries to run exits with a rejection. The [Security Model](/security-model) covers the jail - including its symlink-resolution defense - in full.

**Upgrade the jail script with the package.** `backupkit-remote` is a copy on the archive server, not something the client can update, and it validates every command against the exact name grammar the client uses. So when you upgrade backupkit on a source host, re-copy `dist/snapshots/internal/backupkit-remote.sh` to each archive server it pushes to. A jail older than its client rejects operations with a bare `backupkit-remote: rejected`, which surfaces as a failed run naming no cause. (A test in the package pins the script's grammar to the client's, so the two only diverge across versions, never within one.)

## Running without the jail

The jail is recommended, not required. Set `"jail": false` on a push target to run against a plain account instead:

```jsonc
"nas-www": {
    "direction": "push",
    "remote": "nas",
    "source": "/var/www",
    "destination": "/srv/backups",
    "jail": false  // accepted risk: the push key is not confined
}
```

Two situations call for it:

- **Accepted risk.** You have weighed the threat model and are fine with the push key holding normal account access - for example a LAN NAS that nothing hostile can reach.
- **A restricted host where the jail cannot be installed.** Storage appliances and hosted "storage box" products often offer rsync over ssh but no way to install a script or edit `authorized_keys` forced commands. The jail simply cannot exist there.

Transfers are identical either way. The client always speaks plain `rsync` plus ordinary POSIX commands over ssh - the jail only *validates* them and then executes them verbatim - so removing the jail changes nothing about how a backup runs. For an unjailed target, `backupkit check` skips the `authorized_keys` line and prints a note naming the accepted risk instead. The jail itself is never probed: `check` cannot tell whether the forced command is installed, so installing it (or not) is entirely your act.

What you give up is containment: an unjailed key can do whatever the account allows, including deleting the entire archive in one command from a compromised source host. That is exactly the scenario versioned backups exist for, so prefer the jail - or better, [pull](#why-pull-is-the-safe-default) - whenever you control the archive server.

For a restricted host, the account must accept these commands over ssh, which is what backupkit issues: `rsync --server` (both directions), `mkdir -p --`, `mkdir --`, `mv --`, `find <dir> -maxdepth 1 -mindepth 1 -print0`, `rm -rf --`, `df -Pk --`, and `rsync --version`. If the provider's restricted shell supports those, an unjailed push target works; verify with `backupkit run <target> --dry-run` followed by a real run against a scratch destination.

## What the pipeline does for each direction

Once a target is resolved, backupkit maps its `direction` into a source endpoint and a destination endpoint exactly once, and no downstream code branches on the direction again. Everything after that - the snapshot store, the disk guard, retention, restore - operates on those two endpoints. A pull target has a remote source and a local destination; a push target has a local source and a remote destination. The archive layout is identical either way: snapshots live at `<destination>/<target>/<timestamp>/`, with each run hard-linked against the previous complete snapshot.

Because the mechanics are symmetric, you can mix directions in one config: pull most of your fleet into a central archive, and let a NAT-bound host push to the same archive, all scheduled by the same daemon.
