The `backupkit` binary is a thin view over the engine. Subcommands dispatch through a static table; flags and positional target names are parsed with Node's `parseArgs`. An unknown flag, subcommand, or target name is a hard error that lists the valid names. This page lists every command, its flags, and the exit codes.

## Bare invocation and help

Running `backupkit` with no arguments is a help request, not misuse - it prints the task-oriented setup help and exits 0:

```
backupkit - versioned rsync-over-SSH backups

Setup (3 steps):
    1. backupkit init             write a commented starter config
    2. backupkit check            verify keys, hosts, and versions
    3. backupkit service install  register the daemon (then: backupkit service start)

Commands:
    run [TARGET...]        back up due targets now
    status  [TARGET...]    one row per target: last run, next due
    list    [TARGET...]    complete snapshots (alias: ls)
    restore TARGET SNAP    copy a snapshot to a fresh path
    prune   [TARGET...]    apply retention now
    logs                   tail the daemon logs
    service <verb>         install|uninstall|start|stop|restart|status
    daemon                 foreground scheduler (what the service runs)
    check | init           readiness / starter config
    jail install|status    (on an archive server) install/verify the push jail script

backupkit <command> --help for details.
```

`--help` (and `-h`) prints the same text; `backupkit <command> --help` prints that command's flags. `backupkit --version` prints the version. Every command also accepts `--config <path>` to point at a specific config file.

## Commands

```
backupkit run       [TARGET...] [--force] [--dry-run] [--config P]
backupkit daemon    [--config P]
backupkit service   install|uninstall|start|stop|restart|status [--config P]
backupkit logs      [-f|--follow] [-n N|--lines N] [--config P]
backupkit list      [TARGET...] [--json] [--config P]        (alias: ls)
backupkit status    [TARGET...] [--json] [--config P]
backupkit restore   TARGET SNAPSHOT|latest --output PATH [--verify] [--config P]
backupkit prune     [TARGET...] [--dry-run] [--config P]
backupkit check     [--config P]
backupkit init      [--force] [--config P]
backupkit jail      install|status [--path P]
```

Target names are positional and optional on `run`, `status`, `list`, and `prune`; with none, the command applies to every target.

### run

Back up every due target once, or only the named targets. `--force` bypasses due-ness, backoff, and bucket dedup. `--dry-run` writes nothing and shows what a transfer would move (retention is planned but not executed).

### daemon

Run the foreground scheduler loop - this is exactly what the installed service unit runs. Use `backupkit service` to install and drive it rather than running `daemon` directly.

### service

Manage the OS service unit: `install | uninstall | start | stop | restart | status`. Every verb is idempotent, and `install`, `uninstall`, `start`, `stop`, and `restart` require root; `status` does not. A lifecycle verb with no installed unit says the service is not installed, names the command that registers it, and exits 1. See [Daemon Setup](/daemon-setup) for the full lifecycle.

### logs

Tail the daemon logs - `journalctl -u backupkit` on Linux, a `tail` of the launchd log files on macOS. `-n`/`--lines` defaults to 100; `-f`/`--follow` streams until Ctrl-C. stdio is inherited and the child's exit code passes through. With no log source it says so, names the command that registers the service, and exits 1. There is no `--json` (journald offers `-o json`).

### list (alias: ls)

List complete snapshots per target, oldest first, with a partial-resume indicator. `ls` is the one alias for `list`. A missing archive directory says there are no snapshots yet, names `backupkit run`, and exits 0.

### status

One row per target: last snapshot, next due, last result, consecutive failures, and lock state. Derived from the run reports and the due computation, so it is always instant and needs no root. `service status` adds a unit-state header to the same table.

### restore

Copy one snapshot to a non-existent `--output` path; `SNAPSHOT` may be `latest`. `--verify` runs a post-copy checksum pass. See [Restoring a Backup](/restore).

### prune

Apply retention now. `--dry-run` prints the plan (the keeps with their reasons, then the prune list) and stops without deleting anything.

### check

The interactive readiness gate: validate the config (stopping at the first error), verify local `rsync` and `ssh` versions, load keys, probe remotes, pin unpinned host keys on a TTY, and print the push-jail `authorized_keys` lines (informational: the jail is recommended but optional and never probed; a `"jail": false` target gets a jail-disabled note instead). It exits 2 on a config error and 1 on any probe failure. Run it after each reboot for a `prompt`-passphrase deployment.

### init

Write the fully commented starter `config.jsonc` at the resolved path. It refuses to overwrite without `--force`, naming the config already in the way. Its stdout is three lines.

### jail

The one command meant for the **archive server**, not the push client (install backupkit there too; neither verb reads a config). `install` copies the `backupkit-remote` forced-command script this package ships to `/usr/local/bin/backupkit-remote` (or `--path`) - atomically via a temp file and rename, re-asserting mode `0755`, idempotent, root required. `status` (no root) compares the installed copy against the shipped one and exits 1 when it is missing or outdated - an old copy rejects every push, so pair `npm update -g` with `sudo backupkit jail install`, and use `status` from monitoring to catch drift. The `authorized_keys` lines that point at the script come from `backupkit check` on each push client. As a safety net, **every** `backupkit` invocation on a machine with a script installed at the well-known path prints a stderr warning when that copy differs from the package - a machine with no installed script stays silent. See [the push jail](/security-model#the-push-jail-a-forced-command-that-validates-the-resolved-path).

## JSON output

`--json` exists on exactly the two read-only view commands machines consume: `status` and `list`. Each emits one JSON document on stdout with logs on stderr only. `run`, `prune`, `check`, `service`, and `logs` have no `--json` - the persisted run reports, the printed prune plan, and journald's own `-o json` are already the machine-readable record.

Other output is plain text with columns aligned by padding - no table module and no ANSI color, so everything is greppable. Errors go to stderr as `error <CODE>: message`; stack traces appear only when `logging.level` is `debug`.

## Exit codes

| Code | Meaning |
| --- | --- |
| `0` | success (including bare `backupkit`, `--help`, and idempotent service no-ops) |
| `1` | runtime failure (a target failed, a deletion failed, a probe failed, a lifecycle verb without an installed unit, no logs found) |
| `2` | config error |
| `3` | lock held (try again later) |
| `64` | bad CLI usage (unknown flag, subcommand, or target) |

`logs` passes through the child's exit code when it ran.
