The `backupkit` binary is a thin layer over the engine. An unknown flag, subcommand, or target name is a hard error that lists the valid names, so a typo never turns into a surprise. This page covers every command, its flags, and the exit codes.

## Running it with no arguments

That is a help request, not a mistake. It prints the setup steps and exits 0:

```
backupkit - versioned rsync-over-SSH backups

Setup (3 steps):
    1. backupkit init             write a commented starter config
    2. backupkit check            verify keys, hosts, and versions
    3. backupkit service install  register the daemon (then: backupkit service start)

Commands:
    run [TARGET...]        back up due targets now
    status  [TARGET...]    one row per target: last run, next due
    list    [TARGET...]    complete snapshots (alias: ls)
    restore TARGET SNAP    copy a snapshot to a fresh path
    prune   [TARGET...]    apply retention now
    logs                   tail the daemon logs
    service <verb>         install|uninstall|start|stop|restart|status
    daemon                 foreground scheduler (what the service runs)
    check | init           readiness / starter config
    jail install|status    (on an archive server) install/verify the push jail script

backupkit <command> --help for details.
```

`--help` and `-h` print the same thing. `backupkit <command> --help` prints that command's flags, and `backupkit --version` prints the version. Every command takes `--config <path>` to point at a specific config file.

## The commands

```
backupkit run       [TARGET...] [--force] [--dry-run] [--config P]
backupkit daemon    [--config P]
backupkit service   install|uninstall|start|stop|restart|status [--config P]
backupkit logs      [-f|--follow] [-n N|--lines N] [--config P]
backupkit list      [TARGET...] [--json] [--config P]        (alias: ls)
backupkit status    [TARGET...] [--json] [--config P]
backupkit restore   TARGET SNAPSHOT|latest --output PATH [--verify] [--config P]
backupkit prune     [TARGET...] [--dry-run] [--force] [--config P]
backupkit check     [--config P]
backupkit init      [--force] [--config P]
backupkit jail      install|status [--path P]
```

`run`, `status`, `list`, and `prune` take optional target names. Name none and the command applies to every target.

### run

Back up every due target once, or only the targets you name.

`--force` runs a target whether or not it is due, ignoring backoff and bucket dedup. `--dry-run` writes nothing and shows what a transfer would move; retention is planned but not applied.

### daemon

Run the scheduler in the foreground. This is exactly what the installed service unit runs. Use `backupkit service` to install and drive it instead of running this yourself.

### service

Manage the OS service unit: `install | uninstall | start | stop | restart | status`.

Every verb is idempotent. All of them except `status` need root. Run a lifecycle verb with no unit installed and it tells you the service is not installed, names the command that registers it, and exits 1. See [Daemon Setup](/daemon-setup) for the whole lifecycle.

### logs

Tail the daemon's logs - `journalctl -u backupkit` on Linux, a `tail` of the launchd log files on macOS.

`-n`/`--lines` defaults to 100; `-f`/`--follow` streams until Ctrl-C. stdio is inherited and the child's exit code passes through. With no log source it says so, names the command that registers the service, and exits 1. There is no `--json` - journald already has `-o json`.

### list (alias: ls)

List complete snapshots per target, oldest first, with a marker on any partial snapshot waiting to resume. `ls` is the only alias in the CLI. If the archive directory does not exist yet it says there are no snapshots, points at `backupkit run`, and exits 0.

### status

One row per target: last snapshot, next due, last result, consecutive failures, and lock state.

It is derived from the run reports and the due calculation, so it is instant and needs no root. `service status` prints the same table with a unit-state header on top.

### restore

Copy one snapshot to an `--output` path that does not exist yet. `SNAPSHOT` can be `latest`. `--verify` adds a checksum pass after the copy. See [Restoring a Backup](/restore).

### prune

Apply retention now. `--dry-run` prints the plan - what is kept and why, then what would be deleted - and stops without deleting anything.

`prune` refuses if snapshots have appeared in the archive that no run created (see [the planted-snapshot guard](/retention#the-planted-snapshot-guard)), because retention picks by name and a list with extra names in it would have it delete the real snapshots. Review with `--dry-run`, remove anything that is not yours, then `--force` to prune anyway.

### check

The readiness gate you run before trusting a config. It validates the config (stopping at the first error), checks your local `rsync` and `ssh` versions, loads keys, opens a test connection to each remote, records host keys for unknown hosts when run on a terminal, and prints the `authorized_keys` line for push targets.

That last part is informational: the jail is recommended but optional and is never probed, and a `"jail": false` target gets a note instead.

It exits 2 on a config error and 1 if any connection check fails. Run it after each reboot if any remote uses a `prompt` passphrase.

### init

Write the commented starter `config.jsonc` at the resolved path. It refuses to overwrite without `--force`, naming the config already in the way. Its output is three lines.

### jail

The one command meant for the **archive server** rather than the push client. Install backupkit there too; neither verb reads a config.

`install` copies the `backupkit-remote` forced-command script this package ships to `/usr/local/bin/backupkit-remote` (or `--path`). It writes to a temp file and renames, re-asserts mode `0755`, is idempotent, and needs root.

`status` needs no root. It compares the installed copy against the shipped one and exits 1 if it is missing or out of date - which matters, because an old copy rejects every push. Pair `npm update -g` with `sudo backupkit jail install`, and use `status` from monitoring to catch drift.

As a backstop, **every** `backupkit` command on a machine that has a script at the well-known path warns on stderr when that copy differs from the package. Machines with no script installed stay quiet.

The `authorized_keys` lines that point at the script come from `backupkit check` on each push client. See [the push jail](/security-model#the-push-jail).

## JSON output

`--json` exists on the two read-only commands machines actually consume: `status` and `list`. Each prints one JSON document on stdout, with logs going to stderr only.

`run`, `prune`, `check`, `service`, and `logs` have no `--json`. The stored run reports, the printed prune plan, and journald's `-o json` already cover the machine-readable side.

Everything else is plain text, aligned with padding - no table library and no ANSI color, so it all stays greppable. Errors go to stderr as `error <CODE>: message`. Stack traces appear only when `logging.level` is `debug`.

## Exit codes

| Code | Meaning |
| --- | --- |
| `0` | Success - including bare `backupkit`, `--help`, and idempotent service no-ops |
| `1` | Runtime failure - a target failed, a deletion failed, a connection check failed, a lifecycle verb ran with no unit installed, or no logs were found |
| `2` | Config error |
| `3` | Lock held - try again later |
| `64` | Bad usage - unknown flag, subcommand, or target |

`logs` passes through the child's exit code when it managed to run.
