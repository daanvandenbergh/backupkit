The `backupkit` binary is a thin layer over the engine. An unknown flag, subcommand, or target name is a hard error that lists the valid names, so a typo never turns into a surprise. This page covers every command, its flags, and the exit codes.

## Running it with no arguments

That is a help request, not a mistake. Bare `backupkit`, `backupkit -h`, `backupkit --help`, and `backupkit help` all print the same page and exit 0:

```
Usage: backupkit [options] [command]

backupkit - automated, versioned backups over SSH with rsync, in both directions: push
(the source sends) and pull (the archive server fetches, so a compromised source cannot
touch the archive).

Options:
  -v, --version                          Output the version number
  -h, --help                             Display help for command

Commands:
  run [options] [TARGET...]              Back up due targets now, once
  start [options]                        Foreground scheduler in YOUR session (the home
                                         for encrypted keys)
  daemon [options]                       Foreground scheduler - what the installed service
                                         runs
  service [options] <verb>               Manage the OS service unit (systemd / launchd)
  logs [options]                         Tail the daemon logs
  list|ls [options] [TARGET...]          List complete snapshots (alias: ls)
  status [options] [TARGET...]           One row per target: last run, next due, lock
                                         state
  target [options] <TARGET>              Show one target's settings, as backupkit resolved
                                         them
  remote [options] <REMOTE>              Show one remote's settings, as backupkit resolved
                                         them
  restore [options] <TARGET> <SNAPSHOT>  Copy a snapshot to a fresh path
  prune [options] [TARGET...]            Apply the retention policy now
  unlock [options] [TARGET...]           Clear a destination lock left behind by a killed
                                         run
  check [options]                        Readiness gate: config, binaries, keys, hosts
  init [options]                         Write the commented starter config
  jail [options] <verb>                  (On an archive server) install/verify the push
                                         jail script
  help [command]                         Display help for a command

Setup:
  1. backupkit init             write a commented starter config
  2. backupkit check            verify keys, hosts, and versions
  3. schedule it, either way:
       backupkit start            in this session (the only way for encrypted keys)
       backupkit service install  as a root service (then: backupkit service start)

Run `backupkit help <command>` or `backupkit <command> --help` for a command's own
options.
```

## Per-command help

`backupkit <command> --help`, `backupkit <command> -h`, and `backupkit help <command>` all print the same page: a usage line, what the command does, its positional arguments, and every flag it takes. Commands with verbs (`service`, `jail`) list those verbs too.

```
Usage: backupkit restore [options] <TARGET> <SNAPSHOT>

Copy one snapshot out of the archive into a path that does not exist yet. Restoring never
writes over an existing directory, and never touches the archive.

Arguments:
  TARGET           The target the snapshot belongs to
  SNAPSHOT         A snapshot name from `backupkit list`, or `latest`

Options:
  --output <path>  Path to restore into - must not exist (required)
  --dry-run        Write nothing: run every check and report what the copy would write
                   (cannot be combined with --verify)
  --verify         Re-read the copy and verify checksums afterwards
  --config <path>  Config file to use (default: $BACKUPKIT_CONFIG, else
                   /etc/backupkit/config.jsonc for root, else ~/.backupkit/config.jsonc)
  -h, --help       Display help for command
```

`backupkit --version` (or `-v`) prints the version. Every command that loads a config takes `--config <path>` to point at a specific one.

## The commands

```
backupkit run       [TARGET...] [--force] [--dry-run] [--config P]
backupkit start     [--force] [--config P]
backupkit daemon    [--config P]
backupkit service   install|uninstall|start|stop|restart|status [--config P]
backupkit logs      [-f|--follow] [-n N|--lines N] [--config P]
backupkit list      [TARGET...] [--json] [--config P]        (alias: ls)
backupkit status    [TARGET...] [--json] [--config P]
backupkit target    [TARGET] [--json] [--config P]
backupkit remote    [REMOTE] [--json] [--config P]
backupkit restore   TARGET SNAPSHOT|latest --output PATH [--dry-run] [--verify] [--config P]
backupkit prune     [TARGET...] [--dry-run] [--force] [--config P]
backupkit unlock    [TARGET...] [--force] [--config P]
backupkit check     [--config P]
backupkit init      [--force] [--config P]
backupkit jail      install|status [--path P]
```

`run`, `status`, `list`, `prune`, and `unlock` take optional target names. Name none and the command applies to every target. `target` and `remote` take at most one name: name one and you get its full resolved dump, name none and you get a one-row-per-entry listing of them all.

**Three of these commands run the same scheduler**, and picking between them is the one architectural choice backupkit asks of you. `start` runs it in your session ([Run It Yourself](/run-it-yourself/)); `service` installs and drives it as a root daemon ([Run It as a Service](/daemon-setup/)); `daemon` is the loop that service unit executes, which you rarely type yourself. Of the three, only `start` can unlock a passphrase-protected key and keep a schedule running against it.

### run

Back up every due target once, or only the targets you name.

A target whose destination lock is held is skipped, its run still recorded, and the rest of the pass continues - but the pass then exits 3, so a locked target is never mistaken for a successful one.

`--force` runs a target whether or not it is due, ignoring backoff and bucket dedup. `--dry-run` writes nothing and shows what a transfer would move; retention is planned but not applied. Because it writes nothing it also takes no destination lock, so an estimate works while a real run is in flight - and can never leave a lock behind. The number it reports is a snapshot of that moment, not a reservation.

### start

Run the scheduler in the foreground **in your own session**, for as long as the process lives. Ctrl-C stops it cleanly.

This is the supported home for **passphrase-protected keys**. On startup it launches backupkit's ssh-agent and adds every explicit remote's key to it, prompting on your terminal for each encrypted one; the schedule then runs against that unlocked agent. Everything else - windows, retention, locking, the disk guard - is identical to the service.

Use it when a key has a passphrase, when you want to watch a schedule run before installing it, or on a machine where you would rather not install a root service. Its schedule dies with the process: nothing runs while you are logged out, and nothing comes back after a reboot. See [Run It Yourself](/run-it-yourself/) for the whole mode - which config it reads, where its state lives, and how to survive a logout.

`--force` backs every target up once immediately - the same pass `backupkit run --force` makes, printed the same way - and only then enters the schedule, so you do not have to wait for the first window to see the config work end to end. A failure in that opening pass is reported and the scheduler starts anyway.

Before entering the loop, both `start` and `daemon` print **when each target is next due**, with a note on any target whose time is pushed out by a failure backoff:

```
Scheduler started - 2 of 3 configured targets scheduled. Backups run while this process stays alive; Ctrl-C stops it.
TARGET       NEXT DUE
photos       in 17h
persistance  in 12h    (waiting after 9 failures - see `backupkit status`)
```

Without it a scheduler with nothing due for six hours prints nothing for six hours, which is indistinguishable from one that is stuck. It comes from the same read-only calculation `status` uses, so it costs nothing, and if it cannot be produced the scheduler starts regardless.

### daemon

Run the scheduler in the foreground. This is exactly what the installed service unit runs. Use `backupkit service` to install and drive it instead of running this yourself.

**It refuses to start when any configured key is passphrase-protected**, naming each offending key and remote. A service has no terminal to unlock a key on, so such a key could never be primed - the run would simply fail on every tick forever. A key counts as protected when its remote declares a `passphrase` (`file:` or `prompt`) *or* when the key file itself turns out to be encrypted. Fix it by giving the service a key of its own with no passphrase (`ssh-keygen -t ed25519 -N ""`), or stop the service and [run the scheduler yourself](/run-it-yourself/) with `backupkit start` instead.

### service

Manage the OS service unit: `install | uninstall | start | stop | restart | status`.

Every verb is idempotent. All of them except `status` need root. Run `start`, `stop`, or `restart` with no unit installed and it tells you the service is not installed, names the command that registers it, and exits 1; `uninstall` with no unit is a success - it says there is nothing to remove and exits 0. See [Run It as a Service](/daemon-setup/) for the whole lifecycle.

`install` bakes the resolved config's **absolute path** into the unit's `ExecStart`, so the daemon the OS launches keeps reading that same file. The lifecycle verbs do not inherit it: `start`, `restart`, and `status` re-resolve the config themselves, so repeat the same `--config` on each of them (or export `BACKUPKIT_CONFIG`), or they will rewrite the unit from whatever config they find instead.

### logs

Tail the daemon's logs - `journalctl -u backupkit` on Linux, a `tail` of the launchd log files on macOS.

`-n`/`--lines` defaults to 100; `-f`/`--follow` streams until Ctrl-C. stdio is inherited and the child's exit code passes through. There is no `--json` - journald already has `-o json`. Three states exit 1 with a different instruction each: no unit installed points at `sudo backupkit service install`; a unit that has written nothing yet points at `backupkit service status`; and on macOS a non-root operator is told to re-run under `sudo`, because the log files are root-owned.

It reads the **service's** logs and nothing else. A scheduler you run yourself logs to its own terminal, plus `logging.file` if you set one.

### list (alias: ls)

List complete snapshots per target, oldest first. A snapshot counts as complete only once it has been renamed out of `<name>.partial`, so an interrupted run is invisible here. `ls` is the only alias in the CLI. If the archive directory does not exist yet it says there are no snapshots, points at `backupkit run`, and exits 0.

A [mirror target](/configuration/#snapshot-or-mirror) contributes nothing here: it holds one live copy at its destination and no snapshots at all. Directories inside a mirrored tree are the source's own files, never archive entries, so backupkit never reads one as a listing.

### status

One row per target: last snapshot, how long ago it last succeeded, next due, last result, consecutive failures, and lock state. A mirror target has no snapshot to name, so its `LAST SNAPSHOT` is empty and it never reports a lock (it takes none); everything else on the row works the same, dated from its newest completed run.

Both time columns are **relative** - `20h ago`, `3d 4h ago`, `never`; `in 17h`, `in 3d 4h`, `due now` - because that is what the questions are. "Are my backups current" and "when does this run next" both turn an absolute timestamp into arithmetic you have to do yourself. The exact instants stay in `--json` as `lastSuccessAt` and `nextDueAt`, and the failure block below the table prints the absolute retry time alongside the relative one.

`LAST SUCCESS` counts the newest run that actually backed the source up, which includes a run that finished with warnings (skipped or vanished files still made a backup). It is the only currency signal a mirror target has, since it writes no snapshot. `NEXT DUE` reads `due now` for a time already passed - the target is waiting for the next scheduler tick, at most 30 seconds away - and `-` for a disabled target.

`LAST SNAPSHOT` stays a snapshot **name**, not a time: it is the identifier you hand to `backupkit restore`.

A stale `LAST SUCCESS` next to `0` failures is worth a look: it means runs are being *skipped* rather than failing - a window already fulfilled, a disk-low guard, or a target that is disabled.

The `LOCK` column covers **local** destinations only. A push target's lock lives on the archive server, and probing it would cost an ssh round-trip on a command that promises to be instant, so a push target always reports no lock here - `backupkit unlock` is what reads the real remote state.

Under the table, every target with a failure on record gets a short block saying **why**, taken from the newest failed run - and how to retry it now:

```
persistance last failed at 2026-08-22T16:09:15Z (9 times in a row):
  the destination filesystem is FULL (rsync exit 11) [rsync said: ... No space left on device (28)]
  Waiting until 2026-08-22T22:09:15Z before trying again; `backupkit run --force persistance` retries it now.
```

It reads the newest **failed** report specifically, not the newest report of any kind, so a skip recorded afterwards cannot hide the failure that is still driving the backoff. A healthy target gets no block.

It is derived from the run reports and the due calculation, so it is instant and needs no root. `service status` prints the same table with a unit-state header on top.

### target

Print one target's settings as a `FIELD`/`VALUE` table - **as backupkit resolved them**, not as they are written in the config file. Every default is filled in with the value the next run will actually use, so an option you never wrote still shows up with the value it has. Nested settings are flattened onto dotted paths (`schedule.interval`, `rsync.ioTimeoutSec`, `minFree.percent`); an empty list and an unset value both read `(none)`.

```
$ backupkit target web
FIELD               VALUE
name                web
mode                snapshot
direction           pull
remoteName          box
source              /srv/www
destination         /data/archive/web
exclude             node_modules, .cache
schedule.interval   day
...

Its remote: backupkit remote box
```

The table leaves out the fields that are derived from the ones above it - the resolved remote, and the transfer endpoints backupkit maps from `direction`, `source`, and `destination` - because they repeat the same remote three times. `--json` prints the whole resolved target object, those included, and nothing else.

Name no target and it lists them all instead - one row each, so the names the dump takes are discoverable from the same command:

```
$ backupkit target
TARGET  MODE      DIRECTION  REMOTE  SOURCE    DESTINATION
web     snapshot  pull       box     /srv/www  /data/archive/web
db      mirror    push       box     /var/db   /srv/mirror/db

One target: backupkit target <name>
```

`--json` on the listing prints the whole resolved target array.

### remote

The same dump for one remote. An explicit remote shows its host, user, port, key, passphrase source, `known_hosts` file, and `restrictedShell`; an [ssh_config remote](/configuration/#remotes) shows the alias and nothing more, because the alias is all backupkit knows - `ssh` resolves the rest, and `backupkit check` is what reports what it resolved to. The closing line names the targets using this remote, or says no target does.

Name no remote and it lists them all - kind, the `user@host` (or alias) `ssh` is given, and the targets using each one:

```
$ backupkit remote
REMOTE  KIND      ADDRESS          USED BY
box     explicit  backup@10.0.0.9  web, db
spare   alias     spare            no target

One remote: backupkit remote <name>
```

`--json` prints the resolved remote object on its own, or the whole remotes record when no name is given.

### restore

Copy one snapshot to an `--output` path that does not exist yet. `SNAPSHOT` can be `latest`. `--dry-run` runs every check and reports what the copy would write without writing it; `--verify` adds a checksum pass after the copy. The two cannot be combined - a dry run writes nothing to verify. See [Restoring a Backup](/restore/).

Restoring a mirror target is an error naming its destination: a mirror keeps one live copy and no history, so there is no point in time to restore - copy from the destination directly.

### prune

Apply retention now. `--dry-run` prints the plan - what is kept and why, then what would be deleted - and stops without deleting anything. Mirror targets are skipped: they keep no history to prune.

`prune` refuses if snapshots have appeared in the archive that no run created (see [the planted-snapshot guard](/retention/#the-planted-snapshot-guard)), because retention picks by name and a list with extra names in it would have it delete the real snapshots. Review with `--dry-run`, remove anything that is not yours, then `--force` to prune anyway.

### unlock

Clear a destination lock a killed run left behind. A mirror target always reports nothing to clear - it takes no lock, because the lock directory would sit inside the mirrored tree where the transfer's own `--delete` would remove it.

Each target's archive root is locked for the length of a run, and the release is structural - it happens in a `finally`, so an ordinary failure or Ctrl-C always frees it. A `kill -9`, a lost ssh connection, or a power cut has no `finally`. What is left then depends on where the archive is: a **local** lock records its holder's pid, so the next run sees the process is gone and takes it over by itself. A **remote** lock cannot - there is no pid on this side to probe - so it blocks the target until its 24-hour TTL expires, and one interrupted inside the acquire window (between the lock and its timestamp marker) never expires at all.

That is what this verb is for:

```bash
backupkit unlock                # every target
backupkit unlock persistance    # one of them
```

Each target reports one line: `no lock held`, `lock cleared (...)`, or a refusal.

**A live lock is refused, not removed.** If the holder still looks alive, `unlock` names it and exits 1 without touching anything - two backupkits writing one archive root is the exact thing the lock prevents, and only you can know whether that run is really gone. `--force` clears it anyway. A lock that is already stale (dead holder, or past the TTL) is cleared without `--force`, because that is what the next run would have done regardless.

Exit 1 if any target was left locked or could not be reached.

### check

The readiness gate you run before trusting a config. It validates the config (stopping at the first error), checks your local `rsync` version against the 3.2.5 floor and confirms `ssh` runs, loads keys, opens a test connection to each remote, records host keys for unknown hosts when run on a terminal, and prints the `authorized_keys` line for push targets.

That last part is informational: the jail is recommended but optional and is never probed, and a `"jail": false` target gets a note instead.

It exits 2 on a config error and 1 if any check fails - an unusable local `rsync` or `ssh`, a key that will not load, or an unreachable remote. On a terminal it also unlocks encrypted keys into backupkit's agent, prompting for each - so it is worth running after a reboot on a deployment whose keys have passphrases, though `backupkit start` does the same thing and then keeps the schedule running.

A passing check ends by naming both ways to schedule *this* config:

```
Check passed - backupkit is ready. Schedule it either way:
    in this session:   backupkit start --config /home/dan/.backupkit/config.jsonc
    as a root service: sudo backupkit service install --config /home/dan/.backupkit/config.jsonc
```

Two details there are deliberate. Each command carries `--config` unless the checked config lives in `/etc/backupkit`, because that is the only directory a root service finds on its own - a bare `sudo backupkit service install` after checking a config in your home directory would install a service over root's `/etc` copy, or over nothing at all. And when any configured key is passphrase-protected, the service line is replaced by `NOT POSSIBLE` naming the key, since [a service can never unlock one](/daemon-setup/#a-service-cannot-hold-an-encrypted-key). That is not a failure - the check still passes and still exits 0; only one of the two ways to schedule is open to it.

If any remote is an `ssh_config` alias, it adds a note alongside that service line: the check resolved that alias against *your* `ssh_config` and *your* agent, and a root service resolves it against root's. The note rides with the service line, so a config that also holds a passphrase-protected key prints the `NOT POSSIBLE` line instead and no alias note.

### init

Write the commented starter `config.jsonc` at the resolved path - `--config <path>` or `$BACKUPKIT_CONFIG` when either is set, else `/etc/backupkit` for root and `~/.backupkit` otherwise. It refuses to overwrite without `--force`, naming the config already in the way, and refuses just as firmly when the sibling spelling `config.json` sits in the same directory, since a directory holding both fails to load at all. Its output is three lines.

### jail

The one command meant for the **archive server** rather than the push client. Install backupkit there too; neither verb reads a config.

`install` copies the `backupkit-remote` forced-command script this package ships to `/usr/local/bin/backupkit-remote` (or `--path`). It writes to a temp file and renames, re-asserts mode `0755`, is idempotent, and needs root.

`status` needs no root. It compares the installed copy against the shipped one and exits 1 if it is missing or out of date - which matters, because an old copy rejects every push. Pair `npm update -g` with `sudo backupkit jail install`, and use `status` from monitoring to catch drift.

As a backstop, **every** `backupkit` command except `jail` itself - whose verbs report that state precisely - warns on stderr when the copy at the well-known path differs from the package. Machines with no script installed stay quiet.

The `authorized_keys` lines that point at the script come from `backupkit check` on each push client. See [the push jail](/security-model/#the-push-jail).

## JSON output

`--json` exists on the read-only commands machines actually consume: `status`, `list`, `target`, and `remote`. Each prints one JSON document on stdout, with logs going to stderr only.

`list --json` is an array of `{ target, name, createdAt }` - `createdAt` a full-precision ISO-8601 string. `status --json` is an array of `{ target, lastSnapshot, lastSuccessAt, nextDueAt, lastResult, consecutiveFailures, lockHeld, lastError, lastErrorAt }`, where `lastSnapshot`, `nextDueAt`, and `lastResult` are `null` for a target that has never run (and `nextDueAt` is `null` for a disabled one), `lastSuccessAt` is the full-precision ISO start time of the newest run that backed the source up (`null` when there has never been one), `consecutiveFailures` is a number, `lockHeld` is a boolean that is always `false` for a push target, and `lastError`/`lastErrorAt` carry the explained message and ISO time of the newest **failed** run (both `null` when the target has no failure on record).

`target --json` and `remote --json` each print one resolved object - the same shape the engine runs on, every default already filled in, and for `target` the derived remote and endpoints the table omits.

`run`, `prune`, `check`, `service`, and `logs` have no `--json`. The stored run reports, the printed prune plan, and journald's `-o json` already cover the machine-readable side.

Everything else is plain text, aligned with padding - no table library and no ANSI color, so it all stays greppable. Errors go to stderr as `Error: message`; the machine-readable part is the exit code, not a prefix a person has to read past. Stack traces appear only when `logging.level` is `debug`.

## Timestamps

Every timestamp you read is `YYYY-MM-DDTHH:mm:ssZ` in **UTC**, whole seconds - the `CREATED (UTC)` and `NEXT DUE` columns, the lock details. The trailing `Z` is the ISO-8601 designator for UTC, not decoration: without it the same string would mean *local* time, so a reader in another timezone would misread every backup by their offset. backupkit never prints a host-local time, on purpose - an archive is often read from a different machine than it was written on.

Three deliberate exceptions:

- **Log lines** add milliseconds - `2026-08-10T03:15:00.123Z`. Same format, same timezone, more precision: a busy run emits many lines inside one second, and at second precision their order would be unrecoverable from the log alone.
- **`--json` output and the stored run reports** keep full-precision ISO-8601 (`2026-08-10T03:15:02.123Z`). They are a machine contract, and `jq` and `Date.parse` consumers depend on it.
- **Snapshot directory names** are the same timestamp with the colons removed - `2026-08-10T031502Z`. A `:` is an illegal filename character on exFAT, NTFS and SMB, which is exactly what a USB backup drive or a NAS share is. Seconds are kept because the name is the uniqueness key: two runs in the same minute would otherwise collide.

## Exit codes

| Code | Meaning |
| --- | --- |
| `0` | Success - including bare `backupkit`, `--help`, and idempotent service no-ops |
| `1` | Runtime failure - a target failed, a deletion failed, a check failed, a target was left locked, `start`/`stop`/`restart` ran with no unit installed, no logs were found, `init` found a config already in the way, a root-only verb ran without root, or `jail status` found the script missing or outdated |
| `2` | Config error |
| `3` | Lock held - try again later |
| `64` | Bad usage - unknown flag, subcommand, or target |

`logs` passes through the child's exit code when it managed to run.
