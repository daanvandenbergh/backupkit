By the end of this page you will have backupkit installed, a config that passes validation, and a daemon taking dated snapshots on a schedule. Three commands do the setup: `init`, `check`, `service install`.

**You need:** Node.js 20+, plus `rsync` 3.2.5+ and `ssh` on this machine and on every machine you back up. Step 3 checks the versions for you.

## Install backupkit

```bash
npm install -g @daanvandenbergh/backupkit
```

It has no runtime dependencies beyond Node itself. Check that the binary is on your path:

```bash
backupkit --version
```

Run `backupkit` with no arguments any time and it prints the three setup steps again.

## Step 1: write a starter config

`backupkit init` writes a `config.jsonc` full of comments and stops. It will not overwrite an existing file unless you pass `--force`.

```bash
sudo backupkit init --config /etc/backupkit/config.jsonc
```

It prints three lines: where it wrote the file, and the next two commands. The explanations are in the file itself, so open it next.

Every command looks for the config in the same order: `--config <path>`, then `$BACKUPKIT_CONFIG`, then `/etc/backupkit/config.jsonc` (or `.json`), then `~/.backupkit/`. Pick one location and stick with it.

`init` writes where that same lookup would land: `sudo backupkit init` creates the shared `/etc/backupkit/config.jsonc`, and `backupkit init` as yourself creates `~/.backupkit/config.jsonc` for you alone. The daemon runs as root and cannot see your home directory's config on its own, so if you keep it there, install the service with `--config` - see [Root service, per-user config](/daemon-setup).

## Step 2: edit the config

The starter ships with one example remote and one example target. At minimum you set:

- a **remote** - the machine to connect to. Either spell it out with `host`, `user`, and `identityFile`, or point at an entry in your `~/.ssh/config` with `{ "alias": "myserver" }`.
- a **target** - what to back up. It needs a `direction` (use `"pull"` unless you have a reason not to), a `source`, a `destination`, and a `schedule`.

A minimal pull target:

```jsonc
{
    "remotes": {
        "example": {
            "host": "10.0.0.11",
            "user": "backup-reader",
            "identityFile": "/etc/backupkit/keys/example_ed25519",
        },
    },
    "targets": {
        "var-www": {
            "direction": "pull",
            "remote": "example",
            "source": "/var/www",
            "destination": "/srv/backups",
            "schedule": { "interval": "day", "at": "03:00" },
        },
    },
}
```

The file is JSONC, so `//` and `/* */` comments and a trailing comma are fine. A duplicate key is an error rather than a silently overwritten target.

See the [Configuration Reference](/configuration) for every field, and [Push vs Pull](/push-vs-pull) for why pull is the default.

## Step 3: check it

`backupkit check` is the gate you run before trusting anything. Run it in a terminal, because it is the only command allowed to record host keys and ask for key passphrases.

```bash
sudo backupkit check --config /etc/backupkit/config.jsonc
```

It validates the config, checks your local `rsync` and `ssh` versions, loads your keys, and opens a test connection to each remote. On a terminal it also records the host key of any remote you have not connected to before. For push targets it prints the `authorized_keys` line to install on the archive server.

Fix whatever it reports and run it again until it is clean. It exits `2` on a config error and `1` if a connection check fails.

## Step 4: take one snapshot by hand

Before you hand the job to a daemon, run one pass yourself:

```bash
sudo backupkit run --config /etc/backupkit/config.jsonc
```

That backs up every target that is due. Add `--force` to run a target whether or not it is due, or `--dry-run` to see what would move without writing anything.

Then look at what landed:

```bash
backupkit list
```

Each finished snapshot is a dated directory under `<destination>/<target>/`. Files that did not change are hard-linked to the previous snapshot, so keeping history costs very little disk.

## Step 5: start the daemon

Install the OS service (systemd on Linux, launchd on macOS) and start it:

```bash
sudo backupkit service install
sudo backupkit service start
```

The daemon now runs the scheduler: one snapshot per due window, then a prune against your retention policy. Check on it whenever:

```bash
backupkit status          # last run and next due, per target
backupkit logs            # tail the daemon's log
```
