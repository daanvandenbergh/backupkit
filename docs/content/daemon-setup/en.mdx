The daemon runs the scheduler: one snapshot per due window, then a prune against your retention policy. This page installs it, drives it, tails its logs, and explains what happens after a crash or a reboot.

**You need:** a config that passes `backupkit check` (see [Getting Started](/getting-started)). Every service verb except `status` needs root.

## Install and start it

```bash
sudo backupkit init      # write the starter config
sudo backupkit check     # verify keys, hosts, and versions
sudo backupkit service install
sudo backupkit service start
```

`service install` writes the OS unit - a systemd unit on Linux, a launchd plist on macOS - enables it on systemd, writes a newsyslog rotation rule on macOS, and ends by naming the command that starts it.

## Root service, per-user config

The daemon always runs as **root** - `User=root` in the systemd unit, and the launchd job is a `/Library/LaunchDaemons` system daemon. Two consequences are worth knowing before you point it at a config in your home directory.

**Root looks in root's places.** Under `sudo` the lookup is `/etc/backupkit/` and then *root's* `~/.backupkit/` - never yours. So a config written by an unprivileged `backupkit init`, which lands in your own `~/.backupkit/config.jsonc`, is invisible to it. Name the file once, at install:

```bash
sudo backupkit service install --config ~/.backupkit/config.jsonc
```

The absolute path is written into the unit's `ExecStart`, so every later `start` and `restart` uses that same file. A root service may read a config you own - it only has to be owned by you or root and not group- or other-writable, and `install` refuses it by name with the exact `chmod` otherwise.

**Set `stateDir` explicitly when you do this.** Its default depends on *who runs the command*, not on the config: root gets `/var/lib/backupkit` (`/var/db/backupkit` on macOS), you get `~/.local/state/backupkit`. Share one config between the root daemon and your own unprivileged `backupkit status` and the two read different report directories - the daemon backs up correctly while your `status` shows nothing at all. One line settles it, and both identities then agree:

```jsonc
"stateDir": "/var/lib/backupkit",
```

## One machine, one daemon

`install` writes a single system unit - `/etc/systemd/system/backupkit.service` or `/Library/LaunchDaemons/com.daanvandenbergh.backupkit.plist`. There is no per-user instance, so two people who each keep their own `~/.backupkit/config.jsonc` cannot both have a service: the second `install` overwrites the first one's unit. Pick one:

- **Shared:** merge the targets into `/etc/backupkit/config.jsonc`, the root-owned location every default aims at. One config, one daemon, and no `--config` anywhere.
- **Per-user, unscheduled:** each user keeps their own config and runs `backupkit run` from their own cron or user timer - no root needed. `backupkit daemon` also runs the scheduler in the foreground under their own identity, which a systemd **user** unit or a launchd **LaunchAgent** can supervise.

Mind the order in that second case: `/etc/backupkit/` is probed **before** `~/.backupkit/` for *every* identity, so the moment a shared `/etc/backupkit/config.jsonc` exists it shadows every user's own file. Where both exist, each user's commands need `--config ~/.backupkit/config.jsonc` (or `BACKUPKIT_CONFIG` exported in their shell profile) to reach their own.

Per-user configs stay separate all the way down: each one's `stateDir`, its `<configDir>/known_hosts`, and its agent socket live under that user's home.

## Drive the lifecycle

`backupkit service` takes one verb. Each is idempotent, and each refusal names the exact next command to run.

| Verb | What it does |
| --- | --- |
| `install` | Write the unit (plus enable on systemd, plus a newsyslog conf on macOS) |
| `uninstall` | Stop the unit if it is running, then remove everything `install` wrote |
| `start` | Start the unit. Already up? `Service is already running.` and exit 0 |
| `stop` | Stop the unit. Already down? `Service is already stopped.` and exit 0 |
| `restart` | Restart the running unit |
| `status` | The unit-state header line, plus the per-target table |

Run any lifecycle verb with no unit installed and it says the service is not installed, names the command that registers it, and exits 1.

On Linux the verbs drive `systemctl`; on macOS they drive `launchctl bootstrap` / `bootout` / `kickstart`.

`service status` is the one verb that needs no root. It puts a one-line unit-state header - running with the pid, installed but stopped, or not installed - above the ordinary `status` table, and never errors just because the unit is missing.

### The unit follows your config

Parts of the unit are derived from the config. The important one is `ReadWritePaths`, which lists every path the daemon is allowed to write to: each local destination root, the `stateDir`, the config directory, and the `logging.file` directory.

Under `ProtectSystem=strict` the rest of the filesystem is read-only. So a unit written *before* you added a target would leave the daemon unable to write that target's archive at all.

You do not have to remember this. `start` and `restart` re-derive the unit from the current config; if it differs, they rewrite it, print `config changed since install - refreshed the service unit`, and reload. (On macOS a changed plist is reloaded with `bootout` plus `bootstrap`, because `kickstart` would re-exec the cached one.)

So adding a target is an edit plus:

```bash
sudo backupkit service restart
backupkit service status        # no root needed
```

## Tail the logs

`backupkit logs` tails the daemon's output - `journalctl -u backupkit` on Linux, a `tail` of the launchd log files on macOS. Its stdio is inherited and the child's exit code passes through.

```bash
backupkit logs            # last 100 lines
backupkit logs -f         # follow until Ctrl-C
backupkit logs -n 500     # last 500 lines
```

If there is no log source yet - no journal unit, or no macOS log files - it says so, names the command that registers the service, and exits 1. There is no `--json`, because journald already offers `-o json`.

## Restarts and reboots

The unit is set up so the daemon comes back on its own, while a clean shutdown stays down.

On **systemd**: `Restart=on-failure`, `RestartSec=15`, `StartLimitIntervalSec=0`. A crash or non-zero exit restarts after 15 seconds, a clean exit stays stopped, and systemd never gives up retrying.

On **launchd**: `KeepAlive` set to `SuccessfulExit: false` with `ThrottleInterval: 15` for the same behaviour, plus `RunAtLoad` so the daemon starts at boot.

After a crash or a reboot the daemon rebuilds its picture of the world from the run reports on disk - there is no separate state file. Recovery does four things:

- resumes any in-progress `.partial` snapshot instead of starting over;
- re-derives each target's failure counters from the run reports;
- re-primes `file:` passphrase keys automatically;
- runs exactly **one** catch-up run per missed window.

So a host that was down overnight comes back and takes one snapshot per target, not one per missed hour.

Keys behave differently across a reboot depending on how the passphrase is supplied:

- **Unencrypted keys and `file:` passphrases** need nothing - the daemon reloads them itself.
- **`prompt` passphrases** cannot be re-primed unattended. Only that remote's targets fail, and the error points at `backupkit check`, which is the command to run after each reboot on a `prompt` deployment.
- **Alias remotes** need nothing - your own agent and `ssh_config` are in charge.

## Crash-loop backoff

A target that keeps failing does not spin. Its backoff grows as `15 min * 2^(n-1)` from the consecutive-failure count, capped at 6 hours.

Backoff only ever delays a target's next run - it never stops scheduling it. Every transition (entering backoff, extending it, hitting the ceiling, clearing) is logged at error level. Service-level restarts stay paced at 15 seconds independently of this.

A failing target's `nextDueAt` in `backupkit status` already includes any active backoff, so you can see exactly when it will retry.

## Log rotation

The logger never rotates anything; rotation belongs to the platform.

On Linux that is journald. On macOS, `service install` writes `/etc/newsyslog.d/backupkit.conf` - rotate at 10 MiB, keep 5, compressed - and `uninstall` removes it.
