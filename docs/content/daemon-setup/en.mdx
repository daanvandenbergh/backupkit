There are exactly two ways to run backupkit on a schedule, and this page is one of them: **the OS runs it, as root, unattended** - a systemd unit on Linux, a launchd daemon on macOS. The other is [running the scheduler yourself](/run-it-yourself/) in your own session. They use different commands, different config files, different state directories, and they differ on one hard constraint: **a service cannot hold a key that has a passphrase.**

```bash
sudo backupkit service install
sudo backupkit service start
```

**You need:** root (every verb except `status`), a config in `/etc/backupkit/`, and keys with no passphrase. `backupkit check` tells you whether this config qualifies.

## The whole setup

```bash
sudo backupkit init      # writes /etc/backupkit/config.jsonc
sudo backupkit check     # verify keys, hosts, and versions
sudo backupkit service install
sudo backupkit service start
backupkit service status # no root needed
```

`service install` writes the OS unit, enables it on systemd, writes a newsyslog rotation rule on macOS, and ends by naming the command that starts it. Everything the daemon uses lives in root-owned locations:

| Thing | Where it lives for the service |
| --- | --- |
| Config | `/etc/backupkit/config.jsonc` - or `config.json`, but never both in one directory - the only directory a root service finds by itself |
| Host keys | `/etc/backupkit/known_hosts` (`<configDir>/known_hosts`) |
| Run reports (`stateDir`) | `/var/lib/backupkit`, or `/var/db/backupkit` on macOS |
| ssh-agent socket | `/run/backupkit/agent.sock`, or `/var/db/backupkit/agent/agent.sock` on macOS |
| Unit definition | `/etc/systemd/system/backupkit.service`, or `/Library/LaunchDaemons/com.daanvandenbergh.backupkit.plist` |
| Logs | journald, or `/var/log/backupkit/` on macOS - read either with `backupkit logs` |

A config kept anywhere else has to be named at install time - see [Root service, per-user config](#root-service-per-user-config).

## A service cannot hold an encrypted key

**The service takes only keys with no passphrase.** `backupkit daemon` - the loop the unit runs - checks every configured key before it starts anything, and if any of them is passphrase-protected it exits with an error naming the key and its remote. It does not come up half-working.

That is a property of services, not a policy choice. Unlocking a key needs a terminal to type the passphrase on, and a launchd job or systemd unit has none. The alternative - the passphrase in a file beside the key, readable by the same process that reads the key - buys no secrecy over an unencrypted key while adding a second secret to lose. So the choice is made explicitly rather than papered over.

A key counts as protected when its remote declares a `passphrase` (`"file:/..."` or `"prompt"`) **or** when the key file itself turns out to be encrypted, whatever the config claims.

Two ways forward:

**Give the service its own passphrase-less key.** The usual answer for an unattended backup: a key that exists only for this, with only the access the backup needs.

```bash
sudo ssh-keygen -t ed25519 -N "" -f /etc/backupkit/keys/archive_ed25519
ssh-copy-id -i /etc/backupkit/keys/archive_ed25519.pub backup@archive.example.com
```

**Or keep the passphrase and [run the scheduler yourself](/run-it-yourself/)** with `backupkit start` - the same scheduler, the same windows, the same retention, in your own session where it can prompt.

Alias remotes are unaffected either way: `ssh_config` and an agent are in charge of those, not backupkit. Note that a root service resolves an alias against **root's** `ssh_config` and root's agent, which is a different arrangement from the one your `backupkit check` just verified - `check` says so when it sees one.

## Root service, per-user config

The daemon always runs as **root** - `User=root` in the systemd unit, and the launchd job is a `/Library/LaunchDaemons` system daemon. Two consequences are worth knowing before you point it at a config in your home directory.

**Root looks in root's places.** Under `sudo` the lookup is `/etc/backupkit/` and then *root's* `~/.backupkit/` - never yours. So a config written by an unprivileged `backupkit init`, which lands in your own `~/.backupkit/config.jsonc`, is invisible to it. Name the file once, at install:

```bash
sudo backupkit service install --config /home/dan/.backupkit/config.jsonc
```

The absolute path is written into the unit's `ExecStart`, so the daemon the OS launches reads that file. **Repeat the same `--config` on every later lifecycle verb**, or export `BACKUPKIT_CONFIG` for root:

```bash
sudo backupkit service start   --config /home/dan/.backupkit/config.jsonc
sudo backupkit service restart --config /home/dan/.backupkit/config.jsonc
sudo backupkit service status  --config /home/dan/.backupkit/config.jsonc
```

`start`, `restart`, and `status` re-resolve the config themselves rather than reading it back out of the unit. A bare `sudo backupkit service start` after that install either fails with `no config file found` or - worse, if `/etc/backupkit/config.jsonc` also exists - quietly rewrites `ExecStart` to that other file and reloads, so the daemon backs up from a config you never installed.

A root service may read a config you own: installing as root, the only rule is that the file is not group- or other-writable, and `install` refuses it by name with the exact `chmod go-w` otherwise. Ownership is not checked when the installer is root, since root can read and chown anything regardless.

**Set `stateDir` explicitly when you do this.** Its default depends on *who runs the command*, not on the config: root gets `/var/lib/backupkit` (`/var/db/backupkit` on macOS), you get `$XDG_STATE_HOME/backupkit`, or `~/.local/state/backupkit` when that is unset. Share one config between the root daemon and your own unprivileged `backupkit status` and the two read different report directories - the daemon backs up correctly while your `status` shows nothing at all. One line settles it, and both identities then agree:

```jsonc
"stateDir": "/var/lib/backupkit",
```

## One machine, one daemon

`install` writes a single system unit - `/etc/systemd/system/backupkit.service` or `/Library/LaunchDaemons/com.daanvandenbergh.backupkit.plist`. There is no per-user instance, so two people who each keep their own `~/.backupkit/config.jsonc` cannot both have a service: the second `install` overwrites the first one's unit. Pick one:

- **Shared:** merge the targets into `/etc/backupkit/config.jsonc`, the root-owned location every default aims at. One config, one daemon, and no `--config` anywhere.
- **Per-user:** each user runs their own schedule instead - see [Run It Yourself](/run-it-yourself/), which covers cron, a terminal multiplexer, and supervising `backupkit daemon` from a systemd **user** unit or a launchd **LaunchAgent** under their own uid.

Mind the order in that second case: `/etc/backupkit/` is probed **before** `~/.backupkit/` for *every* identity, so the moment a shared `/etc/backupkit/config.jsonc` exists it shadows every user's own file. Where both exist, each user's commands need `--config ~/.backupkit/config.jsonc` (or `BACKUPKIT_CONFIG` exported in their shell profile) to reach their own.

## Drive the lifecycle

`backupkit service` takes one verb. Each is idempotent, and each refusal names the exact next command to run.

| Verb | What it does |
| --- | --- |
| `install` | Write the unit (plus enable on systemd, plus a newsyslog conf on macOS) |
| `uninstall` | Stop the unit, disable it on systemd, and remove the unit definition (plus the newsyslog conf on macOS). State directories, log directories, and log files are left alone |
| `start` | Start the unit. Already up? `Service is already running.` and exit 0 |
| `stop` | Stop the unit. Already down? `Service is already stopped.` and exit 0 |
| `restart` | Restart the running unit |
| `status` | The unit-state header line, plus the per-target table |

Run `start`, `stop`, or `restart` with no unit installed and it says the service is not installed, names the command that registers it, and exits 1. `uninstall` with no unit is a success instead - `Service was not installed - nothing to remove.` and exit 0.

On Linux the verbs drive `systemctl`; on macOS they drive `launchctl bootstrap` / `bootout` / `kickstart`.

`service status` is the one verb that needs no root. It puts a one-line unit-state header above the ordinary `status` table and never errors just because the unit is missing: running with its pid, installed but not running, not installed, `loaded, no process running right now` on macOS, or whatever state systemd itself reports (`failed`, `activating`) passed through verbatim.

`backupkit daemon` is the command the unit's `ExecStart` runs. You never need to type it yourself on a machine with the service installed; it is documented so the unit holds no mystery.

### The unit follows your config

Parts of the unit are derived from the config. The important one is `ReadWritePaths`, which lists every path the daemon is allowed to write to: each local destination root, the `stateDir`, the config directory, the `logging.file` directory, and - for every explicit remote - the directory holding its `identityFile` and the one holding its `knownHostsFile`, since the daemon creates a missing `known_hosts` and writes the public-key sidecar next to the private key. A key or `knownHostsFile` outside that set does not merely go unhardened; the unit cannot write it at all.

Under `ProtectSystem=strict` the rest of the filesystem is read-only. So a unit written *before* you added a target would leave the daemon unable to write that target's archive at all.

You do not have to remember this. `start` and `restart` both re-derive the unit from the current config and rewrite it when it differs, printing `Config changed since install - refreshed the service unit.` **`restart` is the verb that makes the new unit take effect** - it reloads (on macOS with `bootout` plus `bootstrap`, because `kickstart` would re-exec the cached plist). `start` against an already-running service refreshes the file on disk and then reports `Service is already running.` without reloading anything.

So adding a target is an edit plus:

```bash
sudo backupkit service restart
backupkit service status        # no root needed
```

## Tail the logs

`backupkit logs` tails the daemon's output - `journalctl -u backupkit` on Linux, a `tail` of the launchd log files on macOS. Its stdio is inherited and the child's exit code passes through.

```bash
backupkit logs            # last 100 lines
backupkit logs -f         # follow until Ctrl-C
backupkit logs -n 500     # last 500 lines
```

On macOS the log directory `/var/log/backupkit` is `0750 root:wheel` and newsyslog keeps the files themselves at `640`, so read them with `sudo backupkit logs`.

If there is no log source yet it distinguishes the two reasons: no unit installed (it names the command that registers one), or a unit that has written nothing yet (it points at `backupkit service status`, since the usual cause is a daemon failing to start). Either way it exits 1. There is no `--json`, because journald already offers `-o json`.

This command reads the *service's* logs only. A scheduler you started yourself logs to its own terminal - see [Run It Yourself](/run-it-yourself/#while-it-runs).

## Restarts and reboots

The unit is set up so the daemon comes back on its own, while a clean shutdown stays down.

On **systemd**: `Restart=on-failure`, `RestartSec=15`, `StartLimitIntervalSec=0`. A crash or non-zero exit restarts after 15 seconds, a clean exit stays stopped, and systemd never gives up retrying.

On **launchd**: `KeepAlive` set to `SuccessfulExit: false` with `ThrottleInterval: 15` for the same behaviour, plus `RunAtLoad` so the daemon starts at boot.

After a crash or a reboot the daemon rebuilds its picture of the world from the run reports on disk - there is no separate state file. Recovery does four things:

- resumes any in-progress `.partial` snapshot instead of starting over;
- re-derives each target's failure counters from the run reports;
- re-adds every key to its agent;
- runs **one** catch-up run no matter how many windows were missed.

So a host that was down overnight comes back and takes one snapshot per target, not one per missed hour.

Keys need no attention across a reboot: the service only ever holds unencrypted keys, so it re-adds them itself with nothing to type. That is the practical pay-off of the [passphrase rule above](#a-service-cannot-hold-an-encrypted-key) - unattended really means unattended.

## Crash-loop backoff

A target that keeps failing does not spin. Its backoff grows as `15 min * 2^(n-1)` from the consecutive-failure count, capped at 6 hours.

Backoff only ever delays a target's next run - it never stops scheduling it. Each step is logged right after the failure that caused it, because it carries the one fact that line does not: when the next attempt happens.

```
WARN  waiting 30m before trying this target again target=web failures=2 nextAttemptAt=2026-08-22T03:45:00Z
ERROR this target has failed 6 times in a row - backing off the maximum 6h between attempts target=web failures=6 ...
```

The first five are **warnings**: a failure with a retry already scheduled needs nobody's attention. Reaching the **ceiling** is an **error** - six consecutive failures means the retries are not working and this is no longer something that fixes itself. Clearing the backoff logs nothing: it happens after `backup finished` has already reported the success, so a line there would only make a healthy target's last log entry look like a problem. Service-level restarts stay paced at 15 seconds independently of this.

## Reachability: the network is checked first

Before a due target is dialled, the scheduler checks that its backup server is actually reachable - the local interfaces are up, its hostname resolves, and a TCP connection to its SSH port is answered. Only your configured backup server is probed; backupkit never contacts a third-party "are you online?" service.

If it is unreachable, the target is **skipped, not failed**: one warning naming the cause, no run report, and the failure backoff is left untouched. A run that never happened because the Wi-Fi was down is not evidence about the target - and recording it as a failure is what used to turn one bad night into a wall of errors climbing to the 6-hour ceiling, so that the backup which could finally run when the link came back was still hours from being attempted. Because nothing is backed off, the very first tick after the network returns runs the missed window.

The state is logged on its **edges**: one line when the outage starts, one when it ends. Ticks in between stay silent.

The probe can only ever delay a backup, never stop one, and it never decides that a failure is permanent. A host that answers - even to refuse the port - passes it, as does any probe that cannot reach a verdict, so every real condition still reaches SSH and gets reported properly.

## Severity says who has to act

A failure that reaches the log picks its level from its **cause**, so that a night of flaky internet does not read like a broken configuration:

- **Warning** - a transient failure: no route, DNS did not answer, the connection timed out or dropped. The next attempt may well fix it and there is nothing to do.
- **Error** - a permanent failure: authentication refused, a host key that is not pinned, a host key that changed. It will still be there tomorrow, and it needs you.

So `ERROR` in a backupkit log means something is genuinely wrong, and `grep ERROR` is a useful thing to run. The line that reports a run failing follows the same rule and says what happens next:

```
WARN  backup did not finish - a temporary problem; the next scheduled attempt will try again ranFor="4m 12s" error="..."
ERROR backup FAILED and will not fix itself - every attempt hits the same problem until it is resolved ranFor=3s error="..."
```

## Errors say what actually happened

An exit code names a *class* of failure; the line that says *which* failure is in the program's own output. Backupkit reads that output and puts the reading in the log next to it, so a message names the cause rather than the symptom:

| What the tool said | What backupkit logs |
| --- | --- |
| `rsync error: ... (code 12) at io.c(228)` after `backupkit-remote: rejected` | the backup server's jail refused the command - reinstall it with `backupkit jail` (and it is **not** retried, because a refusal cannot succeed on a second try) |
| `rsync: [receiver] write failed on "...": No space left on device (28)` | the destination filesystem is FULL |
| `rsync: change_dir "/srv/data" failed: No such file or directory (2)` | the source directory could not be entered - it does not exist, or this user may not read it |
| `rsync: --link-dest arg does not exist` | the previous snapshot this run was going to hard-link against is gone; the next run makes a full copy |
| `EXDEV: cross-device link, rename ...` | source and destination are on different filesystems - an archive root must be one filesystem |
| `ENOSPC: no space left on device` | the filesystem is full |
| `mv: ... Invalid cross-device link` on the server | the same, on the backup server |
| `ssh: Could not resolve hostname ...` | the hostname could not be resolved - DNS on this machine or its network, not the host |

The specific cause **replaces** the exit code's generic reading rather than following it, so a message never says the same thing twice; the exit code stays as a parenthetical, because it is the fact that decided whether the run is retried. The raw text is always kept alongside, quoted as `[rsync said: ...]`, `[ssh said: ...]` or `[the server said: ...]` - the explanation is a reading, and the original is the evidence. An error backupkit does not recognise keeps the generic reading and is passed through exactly as the tool wrote it, rather than padded with a guess.

A failing target's `nextDueAt` in `backupkit status` already includes any active backoff, so you can see exactly when it will retry.

## Log rotation

The logger never rotates anything; rotation belongs to the platform.

On Linux that is journald. On macOS, `service install` writes `/etc/newsyslog.d/backupkit.conf` - rotate at 10 MiB, keep 5, compressed - and `uninstall` removes it.
