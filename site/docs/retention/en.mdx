Every backup run is a dated snapshot, and retention rules decide how many of those snapshots you keep over time. This page explains how versioning works and how the grandfather-father-son (GFS) policy chooses which snapshots survive a prune.

## Each run is a hard-linked snapshot

A target's snapshots live at `<destination>/<target>/<timestamp>/`, one directory per run, named by a UTC timestamp. Files that did not change since the previous complete snapshot are hard-linked rather than copied, so an unchanged tree costs almost no additional disk - only changed and new files consume space. The result is a full, browsable copy at every timestamp, with the storage cost of an incremental.

Snapshot names are the single sortable timestamp codec, so "newest" is always well defined and history reads in order.

## A snapshot survives if any rule claims it

Retention is GFS and deterministic: it counts backward through the snapshots that exist, never through a wall clock. A snapshot is kept if **any** configured rule claims it, and each rule records why. The rules, from `RetentionConfig`:

| Rule | Keeps |
| --- | --- |
| `keepLast` | the N newest snapshots, unconditionally |
| `keepHourly` | the newest snapshot of each of the N most recent UTC hours |
| `keepDaily` | the newest snapshot of each of the N most recent UTC days |
| `keepWeekly` | the newest snapshot of each of the N most recent ISO weeks (Monday-start) |
| `keepMonthly` | the newest snapshot of each of the N most recent UTC months |
| `keepYearly` | the newest snapshot of each of the N most recent UTC years |

Each tier walks the snapshots newest-first, computes that tier's UTC bucket key for each, and keeps the first snapshot it sees in each distinct bucket until it has kept N buckets. A snapshot claimed by more than one tier carries every reason - for example `last` and `daily=2026-08-10`.

The starter config ships a sensible default:

```jsonc
"retention": {
    "keepLast": 7,      // the 7 newest, unconditionally
    "keepDaily": 14,    // newest snapshot of each day, 14 days
    "keepWeekly": 8,    // newest per ISO week, 8 weeks
    "keepMonthly": 12,  // newest per month, 12 months
}
```

That keeps dense recent history and thins older history to one-per-week then one-per-month, so a year of daily backups collapses to a few dozen snapshots.

## The newest complete snapshot is always kept

The newest complete snapshot is kept unconditionally, with the reason `newest`, before any rule runs - so a prune can never delete your most recent backup, even if every retention tier is set to zero. This is a hard invariant, not a side effect of the rules.

## Turning retention off

Retention counts are non-negative integers. Two spellings turn pruning off, both deliberate:

- Omit the top-level `retention` object entirely to keep every snapshot forever.
- Set a target's `retention` to `false` to keep everything for that one target, overriding the default.

An empty object (`"retention": {}`) is rejected by the validator - it would be ambiguous, so `false` is the explicit "keep everything" spelling. A target's `retention` replaces the top-level default wholesale; it is never merged.

Schedules and retention are independent. Retention keeps its hourly-through-yearly tiers regardless of how often a target runs; for `minute` and `hour` schedules, `keepLast` and `keepHourly` are what govern sub-daily density.

## Applying retention

The daemon prunes after each run, but you can apply retention by hand at any time:

```bash
backupkit prune              # apply retention to every target now
backupkit prune --dry-run    # print the plan (keeps with reasons, then the prune list) and stop
```

`--dry-run` shows exactly which snapshots each rule claims and which would be deleted, so you can confirm a policy before it removes anything. Pruning runs under the snapshot store lock, and deletion is two-phase, so a prune interrupted midway never leaves a half-deleted snapshot in the archive.
